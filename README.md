# To-Do List Application

A simple, server-rendered to-do list application built with TypeScript, Node.js, Express, and EJS. Tasks are persisted to a local JSON file.

## Features

- Create tasks with a required title and optional description and due date.
- View all tasks and inspect individual task details.
- Edit task titles, descriptions, and due dates.
- Mark tasks as complete or reopen completed tasks.
- Delete tasks with a confirmation prompt.
- Validate user input on the server.
- Persist tasks between application restarts.
- Display helpful validation and not-found messages.
- Responsive interface with keyboard-accessible focus indicators.

## Tech Stack

- **TypeScript** — static typing and improved maintainability.
- **Node.js** — JavaScript runtime.
- **Express** — HTTP routing and application middleware.
- **EJS** — server-side HTML rendering.
- **Zod** — request data validation.
- **JSON file storage** — lightweight persistence without a database.
- **Vitest** — unit and integration testing.
- **Supertest** — testing HTTP routes without starting a separate server.

## Prerequisites

- Node.js and npm installed.
- Git, if you want to clone the repository.

## Getting Started

1. Install dependencies:

   ```bash
   npm install
   ```

2. Start the development server:

   ```bash
   npm run dev
   ```

3. Open [http://localhost:3000](http://localhost:3000) in your browser.

The application creates `data/todos.json` when task storage is first accessed if the file does not already exist.

## Task Data Model

Each task contains the following fields:

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Unique identifier generated by the application. |
| `title` | string | Required task title, up to 200 characters. |
| `description` | string | Optional description, up to 2,000 characters. |
| `dueDate` | string | Optional due date in `YYYY-MM-DD` format. |
| `isCompleted` | boolean | Whether the task is complete; defaults to `false`. |
| `createdAt` | string | Creation timestamp in ISO 8601 format. |

## Architecture

The application separates HTTP handling, business logic, persistence, and presentation.

- **Routes** map HTTP requests to controller methods.
- **Controllers** handle requests, validate submitted data, and choose responses or views.
- **Services** implement task operations and preserve fields that should not change during editing.
- **Repository interface** defines the persistence operations independently of the storage implementation.
- **JSON repository** reads and writes task data to a local file.
- **EJS views** render the task list, creation form, detail page, and edit form.

This structure keeps business logic separate from Express-specific request handling and makes the service and repository easier to test.

## Design Decisions and Assumptions

- **Server-rendered pages:** EJS and standard HTML forms keep the application straightforward without requiring a separate frontend framework or REST API.
- **POST/Redirect/GET:** Successful form submissions redirect to a page instead of rendering a response directly, reducing accidental duplicate submissions when a page is refreshed.
- **JSON persistence:** A JSON file meets the assignment's persistence requirement without introducing database setup or configuration.
- **Server-side validation:** Zod validates task input even when browser-side validation is bypassed. Titles are trimmed and must not be blank, and due dates must be valid calendar dates in `YYYY-MM-DD` format.
- **Stable task metadata:** Editing a task does not reset its completion state or creation timestamp.
- **No unnecessary features:** The implementation focuses on the requested task-management workflows rather than authentication, advanced filtering, pagination, or a separate API.

## Limitations

- JSON file storage is intended for a small, single-process application. It is not designed for multi-process concurrent writes or production-scale workloads.
- The application does not include user accounts or per-user task separation.
- The interface uses standard server-rendered forms rather than a separate single-page application.

## Additional Tradeoffs & Future Improvements

I wanted to keep this project simple while making sure it was organized in a way that would be easy to maintain and build on later.

- **JSON file storage:** I used a JSON file to store tasks so the app would be easy to set up and run without needing a database. If the app grew, I would consider moving to a database like PostgreSQL.

- **Handling multiple writes:** The repository handles write operations one at a time within a single instance to help prevent data from being overwritten. If the app needed to run across multiple servers, I would use a database to handle that more reliably.

- **Simple frontend:** I used EJS templates and standard HTML forms instead of adding a frontend framework. This keeps things straightforward and was enough for the features required in the assignment.

- **Validation and error handling:** I used Zod to validate user input and added centralized error handling for unexpected errors. For a larger application, I would also add more detailed logging and monitoring.

- **Testing:** I added unit tests for the main logic and integration tests for the application routes. If I continued developing the project, I would consider adding browser-based tests to cover the full user experience.

- **User accounts:** I left out authentication and user accounts because they weren't part of the assignment. If the app needed to support multiple users, I would add login functionality and make sure each user could only access their own tasks.

These decisions helped keep the project focused on the requirements while leaving room to expand it in the future.
